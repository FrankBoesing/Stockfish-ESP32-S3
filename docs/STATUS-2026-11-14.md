## Engine runtime configuration

- One Stockfish search worker, pinned to Core 0.
- Arduino setup/loop task runs on Core 1.
- `MaxThreads = 1` remains intentional. A `Search::Worker` occupies about 3,451,840 bytes; after constructing the current engine and its 1 MiB hash, only about 125 KiB PSRAM remained free. Do not enable a second search worker without redesigning/reducing per-worker memory.
- Search pthread stack: 192 KiB, allocated from PSRAM.
- Most recent normal-build stack high-water result: 98,416 bytes minimum free. This is measured for the tested positions, not a guarantee for arbitrary/deep searches.
- The ESP-specific one-tick yield remains throttled to at most once per second so Core 0's IDLE task can service the task watchdog.
- Keep search callbacks lightweight. They execute in the search-worker context; do not call TFT, touch, or other UI/display functions directly from those callbacks. Hand state/events over to the Arduino loop task in a thread-safe, non-blocking way. Do not make the UI loop wait synchronously for a long search.

## PIE accumulator: current default and validation

The 1024-element int16 accumulator update uses the Xtensa ESP32-S3 PIE kernel in the regular firmware.

- Standard environment: `freenove_stockfish_compile`.
- The build defines `STOCKFISH_ESP32_S3_PIE=1` in the base engine environment. Derived O2/O3 and NNUE profiler environments inherit the macro.
- The PIE kernel processes eight int16 lanes per iteration with 128-bit loads/stores and saturating arithmetic.
- Since PIE arithmetic saturates but the scalar Stockfish implementation uses int16 wrap semantics, PIE is selected only when the network-load-time range proof succeeds. If the proof fails, the unchanged scalar path is used automatically.
- This gate is evaluated for the loaded network; do not remove it when working on the GUI or changing network loading.
- The validation environment remains available: `freenove_stockfish_pievalidate`. It computes the PIE result and independently checks all 1024 lanes against the scalar update sequence for each incremental update. Its NPS is not a performance measurement because it deliberately performs extra work.
- On the current Smallnet P_hm network the hardware validation produced:
  - Start position: 41,845 updates, zero mismatching updates/elements, zero out-of-range updates/elements.
  - Kiwipete: 35,108 updates, zero mismatching updates/elements, zero out-of-range updates/elements.
  - Timed search: 6,023 updates, zero mismatching updates/elements, zero out-of-range updates/elements.
  - Total: 82,976 updates × 1,024 lanes = 84,967,424 compared lanes; exact match throughout.
- The validation firmware also completed NNUE verification and all searches without a visible crash/watchdog report.
- The separate build environments `freenove_stockfish_pie` and `freenove_stockfish_piebench` remain as compatibility aliases. Prefer `compile` and `nnubench` for new work.

## GUI startup crash diagnosis — LoadProhibited

A hardware startup crash from the initial GUI build was reported:
Core 1 LoadProhibited, exception 28, fault address 0x00000000. The decoded
backtrace entered `Stockfish::Attacks::Magic::attacks_bb()` while
`Position::set(StartFEN)` ran inside the `Stockfish::Engine` constructor.

Root cause confirmed by comparison with the working diagnostic application:
`src/stockfish_probe.cpp` explicitly initialized both global Stockfish table
sets before constructing `Engine`, while `src/chess_gui.cpp` did not.
The GUI now performs, in this exact order, before the static Engine instance:

1. `Stockfish::Attacks::init()`
2. `Stockfish::Position::init()`
3. `Stockfish::Engine` construction

This matches the initialization sequence in the existing diagnostic probe.
The change is committed as `c29cafdf21b16048798e6cbb987cb3c7ae658cef`.
The corrected firmware has not yet been built or run on hardware; verify the
startup sequence before proceeding with additional GUI features.

## GUI search callback crash diagnosis — std::bad_function_call

A follow-up hardware crash occurred on the first human move, when Stockfish
started its search worker. The backtrace contained
`std::__throw_bad_function_call()` and led through
`Thread::start_searching()` into `Search::Worker::start_searching()`.

Root cause confirmed: the standalone Stockfish Engine API expects the
application to register all five search callbacks. The diagnostic probe did
so explicitly, but the initial GUI only registered `onUpdateFull` and
`onBestmove`. Stockfish invokes `onStart` unconditionally at the beginning
of a search, so the empty `std::function` threw `std::bad_function_call`
inside the pthread and terminated the application.

The GUI now registers explicit no-op handlers for the currently unused
`onStart`, `onUpdateNoMoves`, and `onIter` events, in addition to its
existing `onUpdateFull` and `onBestmove` handlers. This matches the
five-callback registration contract already used by the diagnostic probe.

Fix committed as `15195203bcc600012110629d2ae988c3543838a6`.
Hardware confirmation of the next search is still required.

## Compact game history, draw rules, NVS resume and serial UCI export

Implementation on `stockfish-port-analysis`:

- Replaced the GUI's `std::vector<std::string> gameMoves` with
  `GameHistory`, which stores each move in 16 bits: 6-bit source square,
  6-bit destination square and 3-bit promotion code. The history buffer grows
  dynamically, tries PSRAM first and falls back to internal 8-bit-capable RAM.
  A 200-ply game uses 400 bytes for the move payload.
- The history validates UCI move syntax and supports all four promotion
  suffixes. Stockfish receives a temporary UCI string vector when the current
  position is rebuilt; the compact history is the GUI's single move list.
- Added `Engine::game_status()` to query the live Stockfish `Position`.
  This avoids constructing a temporary FEN-only Position for adjudication
  and preserves the full `StateInfo` chain. The status includes check,
  legal-move availability, the 50-move counter, threefold repetition and
  supported insufficient-material cases.
- The GUI ends a game on checkmate, stalemate, the 50-move threshold,
  threefold repetition or supported insufficient-material cases. It
  automatically adjudicates at the 50-move and threefold claim thresholds;
  an explicit draw-claim action and the automatic 75-move/fivefold thresholds
  are not implemented yet.
- Player colour, skill level and packed moves are stored together in one
  versioned, checksummed NVS blob under namespace `sf-gui`, key `game`.
  It is rewritten after each accepted human move, engine move, undo and
  new-game initialization. Touch calibration remains in its independent
  `touch` key.
- At startup the saved blob is size/version/checksum/syntax checked and moves
  are replayed through `Engine::set_position()`. This recreates Stockfish's
  repetition history. Corrupt or illegal saved games are discarded. If the
  engine is to move after reset, its search is restarted after the game screen
  is shown.
- Serial command `moves` (alias `uci`) prints a UCI
  `position startpos moves ...` line and the current FEN.

## Skill preference persistence and serial move logging

- The menu skill selection is now stored immediately as the independent NVS
  key "skill" in namespace "sf-gui"; changing Level and powering off before
  starting a game no longer loses the selection.
- The per-game saved-game blob continues to include player colour, skill level,
  base FEN and compact UCI history. On restore, the saved game's skill level
  is applied to Stockfish so an interrupted game resumes with its original
  strength setting.
- Completed non-empty serial input lines are echoed to the log as
  [SERIAL] RX: ... before command parsing.
- Every successfully accepted human move and Stockfish move is logged in UCI
  notation, for example [MOVE] Player (White): e2e4 and
  [MOVE] Stockfish (Black): e7e5. Rejected moves and hint suggestions are
  not logged as played moves.
