## Engine runtime configuration

- One Stockfish search worker, pinned to Core 0.
- Arduino setup/loop task runs on Core 1.
- `MaxThreads = 1` remains intentional. A `Search::Worker` occupies about 3,451,840 bytes; after constructing the current engine and its 1 MiB hash, only about 125 KiB PSRAM remained free. Do not enable a second search worker without redesigning/reducing per-worker memory.
- Search pthread stack: 192 KiB, allocated from PSRAM.
- Most recent normal-build stack high-water result: 98,416 bytes minimum free. This is measured for the tested positions, not a guarantee for arbitrary/deep searches.
- The ESP-specific one-tick yield remains throttled to at most once per second so Core 0's IDLE task can service the task watchdog.
- Keep search callbacks lightweight. They execute in the search-worker context; do not call TFT, touch, or other UI/display functions directly from those callbacks. Hand state/events over to the Arduino loop task in a thread-safe, non-blocking way. Do not make the UI loop wait synchronously for a long search.

## PIE accumulator: current default and validation

The 1024-element int16 accumulator update uses the Xtensa ESP32-S3 PIE kernel in the regular firmware.

- Standard environment: `freenove_stockfish_compile`.
- The build defines `STOCKFISH_ESP32_S3_PIE=1` in the base engine environment. Derived O2/O3 and NNUE profiler environments inherit the macro.
- The PIE kernel processes eight int16 lanes per iteration with 128-bit loads/stores and saturating arithmetic.
- Since PIE arithmetic saturates but the scalar Stockfish implementation uses int16 wrap semantics, PIE is selected only when the network-load-time range proof succeeds. If the proof fails, the unchanged scalar path is used automatically.
- This gate is evaluated for the loaded network; do not remove it when working on the GUI or changing network loading.
- The validation environment remains available: `freenove_stockfish_pievalidate`. It computes the PIE result and independently checks all 1024 lanes against the scalar update sequence for each incremental update. Its NPS is not a performance measurement because it deliberately performs extra work.
- On the current Smallnet P_hm network the hardware validation produced:
  - Start position: 41,845 updates, zero mismatching updates/elements, zero out-of-range updates/elements.
  - Kiwipete: 35,108 updates, zero mismatching updates/elements, zero out-of-range updates/elements.
  - Timed search: 6,023 updates, zero mismatching updates/elements, zero out-of-range updates/elements.
  - Total: 82,976 updates × 1,024 lanes = 84,967,424 compared lanes; exact match throughout.
- The validation firmware also completed NNUE verification and all searches without a visible crash/watchdog report.
- The separate build environments `freenove_stockfish_pie` and `freenove_stockfish_piebench` remain as compatibility aliases. Prefer `compile` and `nnubench` for new work.

## GUI work: next phase

The project is now switching focus to the touchscreen chess GUI. The engine optimization baseline should remain unchanged while the GUI is developed.

Current GUI-related groundwork:

- The diagnostic probe in `src/stockfish_probe.cpp` already initializes the ILI9341 display at 320×240 landscape and verifies FT6336U I2C communication.
- The probe can construct the Stockfish engine, verify the NNUE network, run bounded start-position/Kiwipete searches, and run a timed search.
- Touch is currently sampled in the Arduino `loop()` for simple diagnostic output. There is not yet a complete chessboard GUI.
- The current probe is a diagnostic harness, not the final UCI frontend or touchscreen chess application.

Suggested implementation sequence for GUI work:

1. Inspect the current display and touch code, board configuration, and Engine API before restructuring them.
2. Keep display drawing, touch polling, and UI state in the Arduino loop task on Core 1.
3. Keep the search worker on Core 0. Pass search status, principal variation/best move, and completion events to the UI through a small, safe handoff; never render from the worker callback.
4. Implement the board view and basic input first: board coordinates, pieces, selection/highlight, legal move feedback, last move, and status.
5. Add engine interaction after local move entry is reliable: start/stop search, show thinking/best move, apply the engine move, and handle new game/position reset.
6. Keep rendering incremental/partial. Do not allocate a full-screen double framebuffer without rechecking the currently small PSRAM reserve.
7. Test UI responsiveness while the engine searches, and test touch/display behavior during engine start, stop, and search completion.

These are sequencing recommendations, not already implemented features. Confirm the existing source structure/API before choosing a concrete GUI architecture.

## GUI implementation progress — initial prototype

The first interactive GUI implementation has been added on the same
`stockfish-port-analysis` branch. The engine diagnostic target remains
available and unchanged as a separate build environment.

- GUI application source: `src/chess_gui.cpp`.
- Shared ESP trace implementation: `src/esp_trace.cpp`; both the diagnostic and GUI build environments compile it. The former probe-local definition was removed so the GUI does not depend on `stockfish_probe.cpp`.
- GUI build environment: `freenove_stockfish_gui`.
- Build/upload command: `pio run -e freenove_stockfish_gui -t upload`.
- The original `freenove_stockfish_compile` target still builds
  `src/stockfish_probe.cpp`; it remains the known-good engine/NNUE benchmark
  and diagnostic target.
- Visual direction chosen by the user: retain the TeensyFish navy/blue/orange
  palette and compact pixel-game layout, with modest cleanup for 320x240.
- Board orientation: rotate 180 degrees for a Black player so the human side
  remains at the bottom.
- The first menu includes player color and Stockfish skill level selection.
- The board is drawn directly through LovyanGFX; there is no full-screen
  framebuffer.
- Piece artwork uses the 26x26 pixel-art assets from KrisKasprzak/TeensyChess.
  The original 2-bit icons are stored in `src/gui/pieces.h`, with the GPL-3.0-or-later
  attribution retained. `tools/make_chess_icons.js` preserves the vector-to-icon
  generator for regeneration.
- Each occupied square is composed into one 26x26 RGB565 tile and sent using
  LovyanGFX `pushImage()`. The tile buffer uses 1,352 bytes of static internal RAM;
  icon data remains in program flash. Empty squares continue to use `fillRect()`.
- FT6336U touch is calibrated with three points using an affine transform; the
  calibration is persisted in NVS through Preferences.
- A move is entered by selecting a piece and then a destination square. The
  candidate is checked by `Engine::set_position()` using the full UCI move
  history. Stockfish remains the source of truth for legality and position
  state; no second chess-rules implementation is introduced.
- Hint, Undo and New Game controls are present. Engine and hint searches are
  asynchronous; callbacks only copy compact status/best-move data under a
  FreeRTOS critical section. All display and touch handling remains in the
  Arduino loop task.
- First-prototype defaults: 2.4-second engine search, 1.4-second hint search,
  and automatic Queen promotion. These are initial implementation choices,
  not yet tuned or validated on hardware.

**Not yet verified:** the new GUI environment has not yet been confirmed by a
successful PlatformIO build or by an on-device interaction test. In particular,
verify the touch calibration mapping, piece tap coordinates, board rotation,
promotion behavior, search responsiveness and memory/stack headroom. Keep the
existing engine benchmark environment available as a regression reference.
